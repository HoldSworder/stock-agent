规矩：**凡是产出价格、数量、方向的代码，必须有一个跑得起来的检查钉着它。没有检查的，不准进建议区。**

## 现状

`backend/src/scripts/` 下有 63 个文件，约 60 个是自检 / 探针 / 实盘核对脚本。覆盖面不差，但有三个结构性问题：

1. **只有 `glossary:check` 一个 npm 入口。** 其余近 60 个脚本没有 npm script，只能手动指定路径跑。**没有一键跑全部的入口。**

3. **没有常规测试框架**（无 vitest / jest 配置）。保护全靠这些脚本，而它们不会被自动触发。

### B 的复核结果（2026-09-15）

**前复权那条「缺」是误判。** 两套实现都已有检查：
`klineCache.selfcheck.ts` 覆盖 `datasource/adjust.ts` 的 `frontAdjustDaily` /
`frontAdjustMinute`；`modeTrack.selfcheck.ts` 覆盖 `modes/factors.ts` 的 `adjustSplits`。

真正没被钉住的是**两套口径不一致**：

| | `frontAdjustDaily`（实盘链路） | `adjustSplits`（回测链路） |
| --- | --- | --- |
| 判据 | 开盘价对前收向下跳空 | 收盘价比值 |
| 阈值 | 按板别 12%~33% | 固定 0.65 / 1.5 |
| 方向 | 只修向下 | 双向 |

后果是同一只票的历史价在回测与实盘下可能不同，**回测结论不必然适用于实盘**。
这属于重复实现的口径冲突，归入 `issues/11`，不在本工单。

### 补检查时各自查出的缺陷（都已修）

**真实持仓同步**：报价取不到时现价退回成本价，盈亏率随之恒为 0。
而纪律体检拿 `holdRate` 判止损（`holdPct <= -rule.stopLossPct`），
于是**报价一断、止损与止盈永不触发**——实际亏 20% 该止损的票，
会以「持有 0.00%、状态健康」躺在报告里。
改为标出 `priceIsCostFallback`、体检直说判不了并按高优先级提示、
分类计数新增 `priceUnavailable`（不单独计的话它既不算健康也不算命中，会静默消失）。
仓位超配仍照判——那只看市值占比，与现价准不准无关。

**相对强弱排名**：`scoreRotation` 写的是 `(rs ?? 0) * 0.6`，
RS 取不到的 ETF 贡献 0 分、真实落后基准 10% 的贡献 -6 分，
**取不到数的排在真实落后的前面**。与选股「缺失按 50 分」同一个毛病，
而且同一文件的 `classifyState` 已为 `ret20` 修过一次，漏了这处。
改为 RS 或动量取不到就整只剔出榜单，打分函数留断言；
基准取不到会让全榜清空，此时明确说「没有可比的尺子」而不是给个空列表。

**C. 已确认仍存在的错误：模拟层位与建议仓位不一致**

机制已查清：

- `heldPct`（`etfwatch/engine.ts:341`）是已建各层按配置比例求和，护栏用它算剩余仓位（`confirm.ts:290-295`）
- `sizePct`（`confidence.ts:256`）取模型输出，缺省回退到本层目标比例，写进指令并推送展示（`dispatcher.ts:97`）
- 确认建仓后 `applyMutation`（`engine.ts:281-296`）**只增删层号，完全不读 `sizePct`**，下一轮 `heldPct` 按层配置全额计入

**后果**：模型说买 10%、而第三层配置是 40% 时，推送给使用者的是 10%，模拟层位按 40% 记账。关闭模型时 `sizePct` 等于本层目标，两者才一致。

按 `issues/10` 盯盘的模型调用要清零，这个不一致会顺带消失——但**记账口径必须显式定义**，不能靠"模型不参与了所以碰巧对上"。

**已修（2026-09-15）：仓位比例收成规则单一来源。**

不是让记账去追模型，而是反过来——`sizePct` 不再采纳模型输出，一律取本层配置比例。
理由有两条，第二条比第一条重要：

1. 记账闭合：层状态只增删层号、永远按层配置算 `heldPct`，那么推送的数只要等于
   层配置，两侧就恒等。
2. **仓位是个要照着下单的数，属于结论。** 按 ADR 0001/0002，模型只做翻译与
   事实核对，不产结论、不改定版参数。模型仍可在 advice 里说它觉得该轻一点。

连带把提示词与 JSON 契约里的 `sizePct` 一起去掉了：向模型要一个不采纳的数，
只会让它其余的回答围着那个数偏移。手动检测那一路（`analyze.ts`）原先兜底是
硬编码 20%，也改成按层配置算（清仓=当前全部，减仓=撤一层）。

检查：`layerLedger.selfcheck.ts`，逐层核对「推送的数 == 层配置」，
并钉住观望时仓位必须归零、总仓上限护栏仍按同一口径生效。

**D. 另两个待复核的已知错误 —— 已复核（2026-09-14）**

1. **仓位单位：已修复，无需再动。** `plan/service.ts` 有 `pctOf` 辅助函数，注释写明
   「`holdRate` / `positionRate` 存的是小数，直接 `.toFixed()` 加 `%` 会把 30% 的仓位
   印成 0%」，并指出这些文案既进页面也进模型上下文。

2. **未知持仓当空仓：确认仍存在，已修。** 而且当时正在生效——券商 Cookie 失效状态下，
   `decision/service.ts` 的持仓拉取走 catch 后按未持有处理，下游据此告诉模型
   「该标的当前未持有」，并把可选动作限制成**只能买入或观望、不许卖出**。
   后果是：使用者可能正满仓拿着一只该卖的标的，而决策引擎被告知没有持仓、
   并被禁止给出卖出建议——**在最需要它喊撤的时候恰好失效**。

   改为三态 `held / flat / unknown`。unknown 时不假设空仓也不假设持有，
   五个动作都可选，但要求在结论里写明该建议依赖持仓情况、需人工确认。
   四处提示词（单维度研判、Trader 拟单、风险辩论、最终决策）全部按三态改写。

   检查：`holdState.selfcheck.ts`。核心断言是「未知时必须允许卖出」，
   并用穷尽性钉住三态不得退化回布尔——退化后 unknown 会被并进 false 分支，
   未知又变回空仓。

**A. 一键入口：已完成**，见 `issues/10`。`pnpm check` 现状 52 通过、1 跳过。
